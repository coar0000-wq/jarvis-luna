The owner approved implementation, verification and deployment of a limited recovery on 2026-10-23 at 05:06:23 UTC. The policy file records only the bounded scope, an opaque approval reference and its SHA-256 digest. It contains no private conversation transcript. This scope approval does not authenticate missing execution history.

The decision is effective only after the exact implementation and decision bytes have been independently reviewed and committed to authenticated repository main. CI checks the GitHub-authenticated main reference and content-addressed Git objects. CI does not access the private conversation or assert that it cryptographically verified the conversation. Initial expiration is 2026-10-24 at 05:06:23 UTC. Expiration, a code/scope change, an unreviewed run or attempt, a missing baseline member, or incomplete authentication blocks execution. There is no automatic extension, midnight budget reset, STOP expiration or normal-mode fallback.

It summarizes cached quantities/prices, original capture timestamps, explicit blockers and team-review counts, and compares saved rows/bytes to the fixed baseline. ## Authentication and discovery boundary

The production reader requires the current GitHub Actions run ID and attempt, independently verifies its authenticated actor and triggering actor, and rejects a completed historical run being supplied as the current execution. It reads the fixed repository only, over authenticated HTTPS, with redirects denied. No token or signed download URL is copied into reports.

Gap discovery reads **all repository run metadata without branch, status or creation-time filters**, twice. The two complete snapshots must agree. Its upper bounds are 100 pages of 100 runs, 256 metadata requests and a four-minute discovery window, with per-response byte/time limits. A reported count above 10,000, a missing/duplicate page member, a changed total or a changed run/attempt between scans blocks; it never treats the first recent page as complete history.

The reviewed historical inventory binds every pre-approval-cutoff run's ID, attempt, head, workflow and branch by digest. This inventory is collected and reviewed during migration preparation; it is not a claim that a later metadata read reconstructs an exact historical snapshot at the approval timestamp. Missing old runs and changed attempts invalidate the binding. Any observed new or recently updated effect-capable/unknown workflow is blocked unless it is the exact current restricted execution, the exact known input producer, or an already authenticated restricted publication on the same code/decision. Pure verification/Pages workflows have a fixed exception list and must use the exact current or baseline code contract, or an explicitly reviewed prior commit and exact code digest named in the decision. Arbitrary ancestors are not trusted. Current-run retries must also account for every earlier attempt; a running latest attempt cannot hide an unrecorded earlier attempt.

The source of this evidence is GitHub's currently available authenticated records. It is not proof of unrecorded provider activity or the lost runner's local instructions. Metadata that cannot establish the approved inventory is a blocker, not permission to expand it. Deployment review must also check for conflicting writers before activation.

The default is to freeze every canonical data path, including unexpected/new filenames, rather than infer safety from filenames. The shared `data/serpapi_usage.json` provider ledger, product/legal/listing gates and all source budgets are frozen. The exact independently published daily preservation below is the sole explicitly enumerated effect-state overlay; it is not a writable-path allowance. The only advancing profile is the explicitly approved Knowledge workflow and its enumerated non-operations outputs; every restricted execution still leaves every canonical byte unchanged.

An advancing Knowledge input requires its exact successful workflow attempt, single successful job and publication step, approved producer code/policy, bounded plaintext from the exact authenticated job-log endpoint, exact `non_operations` / `excluded_by_profile` publication result and fixed runtime commands. For a normal publisher retry, the original captured checkout remains `base_sha`; the actual direct publication parent is the final validated attempt’s `remote_sha`. Attempt numbers, rejected earlier pushes and ancestor ordering must match. The resulting Git commit must have that exact direct parent, be an ancestor of authenticated main, change only the explicit Knowledge output paths or Obsidian notes, leave all code/effect state unchanged, and preserve every original immutable-history member. New bounded MoE history members may be appended; existing members may never be changed or deleted. The positive job ID must come from the exact attempt jobs response, with exact run/head/job-name binding. The publication marker must occur exactly once in the entire job and fall within the named successful step’s authenticated UTC interval, allowing strictly less than one second after its second-resolution completion time. Missing/reversed timestamps, another marker elsewhere, truncated bodies and oversized responses fail. No guessed job, broad run-log or ZIP-member fallback exists. Redirects carry no Authorization header and are restricted to known GitHub log-storage host families. The known Knowledge and daily plaintext logs were checked against their actual authenticated step intervals locally; this is transport/parser verification, not a successful restricted production execution.

Every canonical data delta from c5 to current main must be attributed to one of these authenticated exact publication commits or the single exact preservation publication below. The bounded first-parent chain is diffed against each commit's explicit first parent, including merge commits. An arbitrary direct-main or merged data change is rejected even if it touches an otherwise eligible Knowledge output. A successful run alone, an output filename alone or a self-reported publication marker from another log step is insufficient.

The code contract covers scripts, configuration, all `.github` content including composite actions, requirements, automation/tools and root files. Any code/policy change invalidates the decision. Latest-main data input authentication compares every protected Git blob/mode with the actual worktree, not counts or a subset of receipt IDs.

The review namespace is separate from canonical history. The publisher must preserve every existing review-history member byte-for-byte, reject malformed history and allow only the exact newly derived member. ## Reports, reuse and publication

The exact generated repository outputs are:

1. `data/agents/continuity_review.json`
2. `data/agents/continuity_review_history/<analysis_id>.json`

No canonical dashboard file is rewritten. The existing public-site builder adds only a small safe status projection to its generated dashboard: unresolved gap, partial-analysis status, false recovery/operations verification flags and the analysis time. Actors, approval references, receipts, nonces, raw private accounting and detailed internal findings are excluded.

The `analysis_id` derives from the decision digest, analyzer code contract and exact saved-input digests. It is independent of run ID. Identical input/code/decision reuses the exact immutable analysis and its original analysis clock. The mutable report can annotate the current authenticated publication run; this is not a new operations task, action, claim or execution receipt.

A report has `mode=restricted_gap`, `continuity=unresolved_gap`, `result=restricted_analysis_complete`, `status=RESTRICTED_ANALYSIS_COMPLETE`, `production_recovered=false` and `operations_execution_verified=false`. The analysis report does not claim successful publication before a push. Only a successful existing-publisher transaction reports `RESTRICTED_ANALYSIS_PUBLISHED`. The collector, release gate and publisher each validate the restricted contract independently. No ordinary required stage is silently removed.

An upload failure after publication cannot erase the already published review and cannot upgrade it to full recovery. Restricted retention uses `restricted-review-<run>-<attempt>`, never a normal safety-checkpoint name. The workflow reports the actual upload outcome separately. No missing upload is called verified retention. A run that reached authenticated main publication can be recognized as restricted even if later evidence export or artifact upload failed; a failure with no authenticated publication remains an additional ambiguous run and blocks. A report's `publication_executions` list is only a lookup hint. Every prior ID, including IDs absent from the latest list-runs page set, must independently prove an exact Core/Deep workflow/main/head/code/decision, an authenticated attempt/job with successful prerequisite stages, a bounded exact publication-step log and the genuine published ancestor commit. That commit must have the authenticated input parent, modify only its exact report/history outputs and contain matching report/result/history bytes. A failed publication step is accepted only when that genuine post-push proof exists. Unknown-workflow, forged Core/Deep and nonexistent IDs never become lineage merely by being written into main JSON.

When main advances, the existing publisher fetches and reanalyzes only exact newly authenticated allowed input bytes. It rejects producer/policy changes, frozen-state changes, stale overlays, decision changes, unknown gaps and expiry. It does not run commerce/operations generation. Push is non-force and bounded to at most two restricted attempts; the existing normal retry limit is unchanged. Publication cannot convert old artifacts into current-run checkpoints.

## API and local verification

The engine is `scripts/continuity_reconciliation.py` and uses only the Python standard library. Its CLI provides `decide`, `analyze` and `validate`, with `--root`, `--execution-id`, optional `--report`, and runner-temporary status output. It has no dispatch, credential creation, provider, approval-writing or remote-write command.

Shared functions include `validate_review_bindings`, `validate_publication_freshness`, `protected_inventory`, `assert_protected_unchanged`, `code_contract_digest`, `load_decision`, `authenticate_evidence`, `validate_decision`, `build_review`, `write_review`, `validate_restricted_report`, `validate_publication_report`, `reanalyze_for_publication`, `restricted_output_paths`, `validate_history_member`, `validate_pending_decision` and `validate_published_review`.

`validate_published_review`, `validate_pending_decision` and `validate_review_bindings` are explicitly offline integrity checks. They retain full code/input/original-history/baseline-findings and immutable-review checks but do not claim a fresh live gap inventory. `decide` only routes a valid restricted decision; it does not call GitHub or authorize publication. The analyzer authenticates two complete snapshots. Standalone aggregate and candidate-quality checks use strict offline binding validation.

The publisher authenticates latest main and two complete run snapshots once per attempt. An in-memory sealed `VerifiedEvidence` is passed to reanalysis, aggregate and both quality phases; serialized flags or dictionaries cannot replace it. Immediately before a non-force push, dry-run success or zero-delta success, `validate_publication_freshness` reads one more complete unfiltered inventory plus exact main/current-run records. It requires the full snapshot digest and actor/run bindings to match, rechecks main at the end, and rejects new executions, old-ID retries, omitted pages or changed metadata. Local review-only commits are allowed; the authenticated remote input commit must remain exact.

The read transport records actual GitHub rate-limit remaining/limit/reset headers and request counts. Missing/invalid headers or insufficient remaining reserve blocks; it never assumes the token starts with 1,000 unused requests. Authentication reserves enough capacity for the final scan (and analysis reserves the following publisher scans); request caps, byte bounds and time bounds still apply. Phase request counts, remaining limits and reserved requests are returned for audit without credentials. With 7,325 runs, each full scan uses 74 listing requests, so the successful analysis + single publisher attempt uses five scans rather than the previous sixteen. Exact totals include bounded attempt/job/log/reference reads and are measured, not inferred as zero. With the named GOSI, Knowledge, exact daily and reconciled blocked Core proofs and no prior restricted publications, 7,325 runs require 163 analysis reads, 163 publisher-authentication reads and 77 final-scan reads: 403 GitHub requests for a successful first attempt, or 643 if a second complete publisher attempt is needed. These are conditional worked counts, not a claim that a live run has occurred. Each independently verified prior publication adds bounded attempt/job/log reads. Hard ceilings are 256 reads per authentication and 103 per final scan; analysis plus two maximal publisher attempts is at most 974 GitHub API reads, and actual remaining/reserve headers can block substantially earlier. Signed GitHub log-storage reads are separately byte/time bounded and receive no token. Test injection is an in-memory transport into the real authenticator, never a saved JSON `verified` flag.

Pages deliberately retains full offline validation. A depth-one Pages checkout needs a bounded fetch of the exact c5 baseline commit/tree before validation. It needs neither the original 52113 Git object nor full history; absent baseline objects fail closed. Fetching that object changes no protected working-tree bytes.
