## 1. Jev: 기존 텍스트 보조 판단을 쓰고 경계 사례를 검증한다

제작자 공개 표는 2026-10-16 실행한 자체 50문제에서 Jev 48/50, GPT-6 Luna 49/50을 보고한다. 한국어 반어 사례는 둘 다 틀렸고, 단순 코드 사례는 입력 전제가 중요하다. 이는 소규모 자체 결과이며 Jarvis 성능이나 영상 제목의 속도 배수를 보증하지 않는다. 독립 재실행하지 않았다.

공식 문서 확인:
- TypeSafe 모델 문서는 jev-1.14.0 선택을 지원하고 비영어 업무는 자사 자료 평가를 권장한다. 현재 별칭 latest/preview를 따라가지 않고 기존 버전 고정을 유지한다.
- 이미지와 Box는 실험 상태이므로 기존 시스템에서 비활성 유지한다. 긴 문맥도 활성화하지 않는다.
- OpenAI Decisions는 typed predicate/choice/score를 제공하지만 이 검토는 신규 연결 지시가 아니다. 현재 Jarvis 공유 계약은 원문·코드·이미지 전송이 아닌 허용된 상태/신선도/근거 존재 집계만 다룬다.

팀별 지시:
- sourcing: 상품 원본·재고 확인의 존재/누락·신선도 집계만으로 보조 판단을 사용한다. 미확인 재고를 '있음'으로 채우지 않는다.
- institutions: 공식 자료의 출처 존재·발행/확인일 누락 건수를 점검하고, 모델 점수로 기관 승인이나 규제 준수를 확정하지 않는다.
- market: 한국어 반어·혼합 평가를 사람이 표시한 로컬 평가 사례로 준비한다. 현재 공유 API에는 고객 리뷰 원문을 추가 전송하지 않는다.
- listing: 정본 ID·라벨·고시·출처 증거의 누락을 먼저 로컬 검사하고 보조 판단은 source_check/human_review 경로만 제안하게 한다.
- pricing: 통화·원가·수수료 누락과 비용 계산은 결정적 로컬 검사로 처리한다. 공급자 단가와 실제 잔액·자사 비용을 분리한다.
- legal: 고위험 누락을 통과시킨 오판을 별도 집계하고 법률·게시 승인은 사람이 결정한다. 높은 확률도 승인 근거가 아니다.
- robotics: 허용된 오류/상태 집계로 로컬·출처 확인·사람 검토 경로를 점검한다. 원시 로그·코드·자격증명 전송이나 도구 권한 확대는 하지 않는다.
- design: 참고자료·실물/라벨 검수의 완료/누락 집계만 기존 텍스트 계약에 사용한다. 이미지·Box·긴 문맥을 활성화하지 않는다.
- channels: 게시·고객 발송·결제 게이트의 미충족 상태를 그대로 유지한다. 모델 권고를 실행 승인으로 승격하지 않는다.
- knowledge: 팀별 정상·누락·충돌·불명 사례와 사람이 정한 기대 경로를 로컬 평가표에 기록한다. 향후 허용된 실호출의 응답 모델·지연·토큰·오판을 별도로 기록한다.
- graph: 원본 근거 없는 관계는 unknown으로 보존하고 근거 존재/누락 집계를 평가한다. 모델의 확신을 새 사실이나 관계 증거로 저장하지 않는다.

산출물: 각 팀은 정상·누락·충돌·불명 사례에 입력 조건, 근거, 사람의 기대 경로(local/source_check/human_review), 실제 관찰/미실행 상태를 기록한다. 새 모델 호출·범위 확대 없이 로컬 검토부터 진행한다. 하드 게이트 누락을 통과시킨 사례는 0건이어야 다음 단계 검토가 가능하다. 이것은 정확도 달성 선언이 아니다.

## 2. Shopify: 대기자/재입고 알림 파일럿을 승인 전에 설계한다

영상 설명은 앱 스토어 검색→기능/가격/리뷰 비교→선택→설정의 일반 절차다. 특정 앱이나 상품 옵션별 자동 재입고 기능이 검증됐다고 주장하지 않는다. 업로더 챕터 00:25와 00:58은 비교·설정 위치를 찾는 힌트다.

공식 Shopify 문서는 설치 전 개인정보/스토어 데이터 접근과 개인정보처리방침 검토를 요구한다. Forms는 관심 등록용 폼 대안으로 검토할 수 있으나 옵션별 재입고 알림 시스템과 동일하다고 가정하지 않는다. Forms의 마케팅 동의 설정은 별도 선택 사항이므로 알림 신청을 일반 마케팅 동의로 바꾸지 않는다.

팀별 지시:
- sourcing: 파일럿 후보 1개를 정본 상품 ID와 variant ID에 연결하고 실제 재고·재입고 근거·예정일 미확인을 구분한다. 수요 등록 수를 확정 주문으로 보지 않는다.
- market: 재입고 알림 요청과 일반 마케팅 구독 목적을 분리한 문안을 작성한다. 허위 품절·가짜 대기자 수·확정되지 않은 출시일은 넣지 않는다.
- listing: 품절/출시예정 상태, 정확한 옵션, '알림 신청은 예약·구매 아님' 문구를 초안 명세에 넣는다. 판매·법률 게이트를 유지한다.
- pricing: 필수 기능, 무료 한도, 월/연 결제, 사용량 요금, 해지·데이터 내보내기 조건을 후보별로 비교한다. 이번 지시로 구독하거나 결제하지 않는다.
- legal: 수집 항목·목적·보유기간·철회/삭제 경로·개인정보처리방침·권한을 검토한다. 알림 동의를 다른 마케팅 동의로 간주하지 않는다.
- robotics: 합성 데이터로 정상/중복/잘못된 이메일, 옵션 변경, 해지 후 발송 차단, 중복 이벤트, 재고 0 상태를 테스트할 계획을 작성한다. 실제 고객 발송은 별도 승인 대상이다.
- design: 모바일 폼의 오류·성공·이미 신청·취소 상태와 명확한 옵션 표시를 비공개 초안으로 정의한다. 실제 테마에는 적용하지 않는다.
- channels: 요구사항에 맞는 Shopify 앱 후보와 공식 Forms의 단순 관심 등록 대안을 비교한다. 상품 옵션별 재입고 트리거·중복 방지·해지 억제를 확인하고 앱 설치/권한/실발송은 승인 전 실행하지 않는다.
- knowledge: 결정표·검수자·미확인 사항·파일럿 합격 조건을 기록한다. 내부 브리핑 배포, 앱 설정, 실제 고객 테스트의 증거를 각각 분리한다.
- graph: 정본 상품/옵션 ID와 폼/이벤트 매핑을 설계하되 고객 이메일이나 개인정보는 공개 피드·그래프·모델 상태에 저장하지 않는다.

필수 파일럿 합격 조건:
- 대상 정본 상품 ID·variant ID·재고 근거가 확인되고 출시/재입고일 미확인을 표시한다.
- 개인정보 최소 수집, 사용 목적, 동의, 철회/삭제, 중복 방지, 선택 옵션 매핑을 문서로 검토한다.
- 합성 데이터로 정상·잘못된 이메일·중복·옵션 변경·철회·중복 이벤트·재고 0을 검사한다.
- 앱 설치, 권한 부여, 유료 플랜, 실제 고객 데이터 수집/발송, 실제 테마/상품 활성화 전 해당 승인을 받는다.
- 가입 수를 주문/매출/효능 검증으로 보지 않는다. 실제 파일럿 결과는 실행 후 별도로 기록한다.

## 공유와 실제 사용 증거

원본은 team_youtube_insights.json과 team_briefings.json에 둔다. 기존 learning/feed/brain 생성기가 이를 읽는다. 데이터만 추가한 상태는 지시 준비이며, 생성물의 영상 ID와 대상 팀을 확인한 후에만 팀 공유 완료로 기록한다. 다음 회차 팀 산출물이나 검증 영수증이 있어야 실제 사용 완료라고 말할 수 있다.

기존 Jev 1.14 업그레이드 브리핑은 보존한다. 이 항목은 평가·업무 지시 보완이며 중복 업그레이드가 아니다. 결제·설치·권한·API 호출·고객 발송은 수행하지 않았다.
