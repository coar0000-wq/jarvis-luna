# JARVIS 운영 시스템

도윤 -> 기존 비서실장 -> 기존 11개 팀장 -> 전문 기능 구조를 유지한다. 아래 8개는 새 조직 에이전트가 아니라 시스템 기능이다.

| 기능 | 실제 구현 |
|---|---|
| Manager | 기존 비서실장 제어, 고정된 보고서 목표 분해와 실행 순서 관리 |
| Router | 기존 팀 ID 검증 및 안전한 읽기/보고서 의도 라우팅. 알 수 없는 의도는 차단 |
| Task | 안정 ID, 의존성, 상태 전이, 목표당 32개/깊이 6 한도 |
| Handoff | 전문 기능의 제안 후 비서실장만 수락. 부모 실행증거와 순환 검증 |
| Watch/Event | 실제 캡처 시각과 의미 있는 변경 확인, 중복 제거/쿨다운. 진짜 가격 변경 이벤트만 생성 |
| Approval | 정확한 대상/내용/정책/증거/nonce/만료를 신뢰된 사람 검증기에 결합 |
| Execution | L1 로컬 읽기와 L2 스냅샷 보고서만 허용. 디스크 예약 후 실행, 출력 해시 재검증 |
| Knowledge/Feedback | 실제 결정, 작업, 인계, CP, 실행 영수증 관계 및 동일 지표/단위/코호트/기간 피드백 |

## 실제 동작과 한계

`python scripts/run_jarvis_operations.py`는 오프라인 로컬 루프다. Core/Deep 및 최종 공유 퍼블리셔에 연결된다. 기존 source 수집 워크플로는 별도로 유지한다. GitHub Actions 예약 실행은 best-effort이며, 상시 서버 또는 실시간 주문 수신을 의미하지 않는다.

보고서가 존재하고 해시와 권위 있는 실행 장부가 일치해야 COMPLETED가 된다. 보고서의 완료는 새로운 원천 수집, 판매 완료, 법률 승인 또는 사업 개시 허가가 아니다. 원천 캡처가 없거나 오래됐으면 그대로 unknown/BLOCKED이다. `generated_at`을 원천 수집 시각으로 쓰지 않는다.

- `data/operations/state.json`: 지속 상태와 불변 이벤트/결정/영수증
- `data/operations/reports/.execution-ledger.json`: 예약과 확인된 로컬 실행 영수증
- `data/operations/board.json`: 안전한 요약, 기존 dashboard_runtime.operations로 투영
- `data/operations/knowledge_graph.json`: 실제 관계 그래프
- `data/operations/feedback.json`: 실측 비교 결과. 현재 실제 판매 관측은 없으므로 학습/승격하지 않는다.

이 저장소에는 자유 형식의 개인 목표, 승인 서명키, 고객 개인정보 또는 비밀정보를 기록하지 않는다. 사용자 채팅/음성의 인증된 목표 접수, 주문/고객 이벤트 및 실제 판매 관측 커넥터는 아직 연결하지 않았다.

## 승인과 외부 실행

평문 JSON의 approved/approved_by, 정적 사이트 버튼 또는 모델 판정은 사람의 권한을 증명하지 않는다. 공개 화면은 읽기 전용이고 승인/실행 권한을 부여하지 않는다.

현재 신뢰된 승인 검증기와 외부 커넥터가 설정되지 않았다. L3 일반 수정 훅 및 모든 L4 실행은 서버 레지스트리에서 비활성이다. 기존 deterministic Safe Auto-Fix는 기존 좁은 허용 범위로 별도 유지하며, 그 표시용 로그를 새 실행 영수증으로 재분류하지 않는다.

Shopify 초안 생성도 외부 쓰기인 L4다. 결제, 재고 변경, 공개 게시, 외부 메시지/광고, 삭제를 승인 없이 실행하지 않는다. 실제 외부 기능을 연결하려면 별도 검토된 커넥터, 인증된 사람 승인, 대상과 완전한 immutablePayload, 멱등성/재조정이 모두 필요하다.

지속 예약 이후 중단/불명확한 결과는 RECONCILIATION_REQUIRED로 전역 중단하며 자동 재시도하지 않는다. 오래된 lock도 자동 삭제하지 않는다. 안전한 멱등 읽기에만 1회 재시도를 허용한다. Jev 인증/크레딧/할당량 오류에는 재시도하지 않는다.

## Shopify 최종 증거 순서

상위 원천/점수/가격/카피와 CP 정본 생성 후:

`legal_full -> 임시 gate -> master --inject-s -> shortlist -> MoCRA -> 최종 gate -> exporter -> action queue`

공유 `prepare_commerce_export.py`가 이 순서를 오프라인으로 수행한다. 최종 gate는 추천 행 갱신 후 현재 입력을 서명한다. 그 뒤 입력이 바뀌면 exporter는 어떠한 출력도 변경하기 전에 차단한다. 온톨로지/카피/목록/법률/MoCRA/라벨과 실행 대상/API/원격 전제 조건을 결합하며, Draft/비공개/재고 0/deny/cap/CP 정체성과 후보 분리를 유지한다.

## Jev와 비용

Jev는 구조화된 보조 평가 도구다. 실제 파일/API/브라우저 실행 엔진이 아니다. 기존 shared-free 어댑터와 계정 연결/24시간 무료 잔액 증빙/누적 한도/캐시/예약/중단 규칙을 유지한다. 신규 결제나 크레딧 구매, auto-refill, 유료 override를 허용하지 않는다. 증빙이 없거나 만료되면 로컬 보조 판정으로 돌아간다.

영수증 전환은 로컬 커밋 시각이 아니라 보호된 릴리스 커밋의 run.head_sha 계보로 구분한다. 미확인 계보는 차단하고 기존 한도/사용량/중단 상태를 초기화하지 않는다. 별도 Jev 잔액 확인 루틴은 사용자 중지 상태를 유지한다.

## 사업 준비와 기술 준비

MoCRA 상태는 별도의 원천 증거다. 이 구현은 sales_allowed를 자동으로 열지 않는다. 저장된 미완료 규제 항목과 실제 재고/원격 계정/출시 승인을 해결하기 전에는 사업 개시 가능하다고 보고하지 않는다. 예측 확률과 판매 개수를 직접 비교하지 않으며, 첫 판매 관측이 없다고 판매 0건을 관측했다고 만들지 않는다.

## 개발 우선순위와 감사 연결

Task Engine -> Team Handoff -> Approval Gate -> Audit Log -> Watch/Event -> Jev 연동 -> Knowledge Graph/Feedback 순서로 진행한다. 실행기와 증거 검증은 모든 단계의 안전 조건이다. Jev 판정이 승인이나 실행 권한으로 승격되지 않는다.

Audit Log는 미래 전용이다. 기존 이벤트, 판단, 영수증과 정확한 보고서 바이트를 소급 변경하지 않는다. 새 로컬 작업은 판단/증거를 저장한 뒤 EXECUTING으로 전이한다. 정확한 `make_action` 내용은 비공개 `state.audit.payloads`에 action_hash로 저장하고, 준비와 결과를 불변 companion 이벤트로 연결한다. 이유/코드, 역할, 증거 해시, 인계/판단/내용/영수증 참조, 승인 상태와 실패 결과가 연결된다. 해시와 역할 문자열은 인증 증명이 아니다.

- L1/L2 승인 상태: `not_required_local`. 그 밖에는 `unavailable`이며 실제 승인 검증기는 미설정이다.
- 실패/차단 결과는 비공개 감사 결과에 남지만 신뢰된 완료 영수증 장부로 승격하지 않는다.
- EXECUTING 재시작은 기존 확인된 장부를 읽어 재조정하며 기록이 없다고 재실행하지 않는다.
- 원본 payload, rationale, nonce, 승인 증명, 비공개 상태는 공개하지 않는다. 공개 화면은 수량 요약만 표시한다.
- 연속 복원은 모든 과거 기록/activation을 보존하고 감사 head만 검증된 append 체인으로 전진한다.
- `--goal`은 기존 11팀의 제한된 로컬 보고서 목표명이다. 대화 목표의 인증 접수나 외부 권한을 대신하지 않는다.

## 11팀 개선 증거와 지속 루프

모든 팀을 감시하지만 모든 팀의 실측 개선이 확인됐다는 뜻은 아니다. `team_improvement_evidence`는 감시, 내부 제안/자료 대기, 보고된 그림자 검증, 적용된 제한 정책, 차단을 구분한다. 현재 독립 검증된 성과 개선은 0이며 자동 학습, 매출 개선 또는 법률 통과를 추정하지 않는다.

기존 제한 정책 시험은 그래프/분류, 소싱, 디자인 3개다. 그래프 512 -> 507 / 6,955는 같은 입력의 분류 규칙 그림자 보고이며 사업 성과가 아니다. 소싱 3/110 -> 10/110은 적용 후 관찰 1회로 지속적 인과 개선을 증명하지 않는다. 디자인 cap 적용/7개 제외는 전후 품질 개선 비교가 아니다. 다른 팀에는 비교 가능한 지표/단위/코호트/관찰 기간과 독립 피드백이 먼저 필요하다. 내부 제안만으로 코드, 전략, 승인, 예산, 모델을 자동 변경하지 않는다.

Core와 Deep의 기존 생성 루프는 각 팀의 실제 입력/차단을 다시 읽어 안전한 증거 투영을 갱신한다. 문구 변경이나 조치 소멸은 개선/원천 복구 증거로 쓰지 않는다. 생성/실행 시작/정책 적용 시각을 실제 캡처나 독립 평가 시각으로 바꾸지 않는다. 진단 회차를 자동 prune하지 않으며 8MiB 용량에 도달하면 명시적으로 중단한다. 기존 원천 절차의 2시간 쿨다운, 장애당 2회, lifetime/회차 예산, lock, 중단과 재조정 규칙은 그대로 유지한다.

## 동일 범위 다이소 복구

1개 무변경 실행과 shortlist 가격 관찰은 110개 기본 discovery 발행 장애를 해소하지 않는다. 전체 복구는 실제 GitHub run/attempt/main/workflow, 성공한 수집/검증/정본 보존/발행 단계, 아카이브 digest 및 현재 정확한 원천 바이트를 재검증해야 한다. 과거 실패의 범위도 인증된 원본으로 확인하며 모르면 차단 상태로 둔다. operating capture 최신성, 비교 후보 수집, shortlist 가격, 좁은 발행과 전체 workflow는 별개다.

candidate_pool의 마지막 실행 목록 교체는 제품 삭제가 아니다. 제품 정체성과 근거 필드는 보존하고 HEAD/이전/현재 정확한 풀 스냅샷을 불변 SHA 파일로 남긴 뒤 마지막 실행 메타데이터 교체만 정확한 base/replacement 해시의 사유 manifest로 허용한다. 원본 아카이브나 사유가 없으면 발행을 차단한다. 수집/비교 복구는 판매 허가가 아니다.

## Shopify 향후 위임과 사업 피드백

가입/설정 완료는 포괄적인 실행 승인이 아니다. Shopify Checkout WebMCP는 구매자 브라우저의 checkout 도구이며 구매자 확인이 필요하고 판매자 관리 권한을 부여하지 않는다. 등록 전 제품명/정확한 variants, 통화/가격, 무게/배송/재고, 이미지, 설명, 성분/라벨, 제조사 안전성 및 책임자 근거, 원천 캡처 참조를 구조화한다. 제품별 법률/라벨 증거와 대상 shop/API/원격 전제 조건, 정확한 immutablePayload, 사람 승인, 멱등성/재조정을 검증한다.

Draft 생성도 L4다. 공개 발행, 재고, 주문, 결제, 광고, 메시지, 삭제는 승인 없이 실행하지 않는다. 실제 매출/전환/반품/수수료/원가/순이익의 동일 기간 관측을 먼저 연결하고 예측과 비교한다. 관측이 없으면 unknown이며 매출 0이나 성공 확률로 만들어내지 않는다. 자동화는 성공적인 사업이나 수익을 보장하지 않는다.

GitHub의 정수 초 단위 완료/검증 메타데이터는 해당 초의 반개구간으로 검사한다. 실제 원천 캡처의 소수점 시각은 변경하지 않는다. 생성/dispatch 메타데이터의 1초 역전은 별도 precision 항목으로 보고하고, 그보다 크거나 미래인 시각은 차단한다.

운영 state는 공백만 줄인 JSON으로 저장하며 8MiB 한도를 유지한다. 모든 판단/이벤트/내용/시각/영수증은 그대로이고 자동 prune/reset을 하지 않는다. 인증된 특정 과거 ZIP의 oversized state는 원본 ZIP 및 SHA를 보존하고, 고정 digest·정확한 원본/compact 크기·SHA·엄격한 객체 동일성·기존 총량/멤버/파일 한도를 모두 만족하는 제한된 공백 변환만 허용한다. 일반 oversized 아카이브는 계속 차단한다.

Watch의 원본 entity 이벤트는 모두 보존한다. 같은 관측에서 발생한 다수 이벤트는 기존 팀별 불변 event_batch 참조로 묶어 하나의 제한된 로컬 보고서 작업으로 검토한다. 원본 event ID/근거/시각을 삭제하거나 성과 개선으로 바꾸지 않는다. 묶음 참조와 정확한 event ID 목록의 해시는 무결성 증명일 뿐 승인 권한이 아니다.

Git subtree ZIP의 CRLF export 문제는 검증용 TMP에서 원본 Git blob·receipt hash·authenticated Deep 바이트가 일치할 때만 복구했고 실제 운영 기록을 바꾸지 않았다.
